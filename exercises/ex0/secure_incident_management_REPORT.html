SQL Injection in fetchCustomer Critical
A05:2025 Injection Impact: Severe Ease: Easy AdminService

Description

AdminService.fetchCustomer in srv/services.js accepts a user-supplied customerID parameter and interpolates it directly into raw SQL strings via template literals, then executes them via cds.run(). Both the concat method (line 40) and the tagged method (line 62) are vulnerable — the tagged method uses a pseudo-tagged template helper that degrades to plain string concatenation. An attacker supplying ' OR '1'='1 causes the WHERE clause to evaluate as always-true, returning all customer records including credit card numbers, email addresses, and phone numbers.

Evidence

  • srv/services.js:40 — `SELECT * FROM sap_capire_incidents_Customers WHERE ID = '${customerID}'` — direct template literal interpolation into SQL (concat method)
  • srv/services.js:62 — same interpolation via pseudo-tagged template that returns a plain string (tagged method)
  • srv/services.js:43 — cds.run(vulnerableQuery) executes the raw SQL string
  • In-code comments at lines 36 and 52 explicitly flag both methods as ❌ VULNERABLE

Attack Precondition

Attacker holds the admin role (XSUAA JWT in production). In development mocked-auth mode, incident.support@tester.sap.com / initial is assigned the admin role and can exploit this immediately without any additional steps.

Recommendation

  1. Replace both query methods with CAP's parameterized query builder: SELECT.from(Customers).where({ ID: customerID })
  2. Never pass user-supplied values as raw SQL string fragments to cds.run()
  3. Remove the method parameter entirely and implement a single secure lookup path
  4. Add input validation (UUID or alphanumeric format check) on customerID at the API boundary

Missing Row-Level Access Control on Incidents — Horizontal & Vertical Escalation Critical
A01:2025 Broken Access Control A06:2025 Insecure Design Impact: Significant Ease: Easy ProcessorService

Description

🔁 Horizontal Escalation — Exercise 1.1: ProcessorService.Incidents in srv/services.cds:8 is annotated with only @requires: 'support' — no @restrict where clause. Any authenticated support user can read, update, or delete any incident in the system, with no ownership restriction.

⬆️ Vertical Escalation — Exercise 1.2 (DELETE): srv/services.js:6 registers this.before("UPDATE", "Incidents", ...) only. No this.before("DELETE", ...) guard exists. A support user can DELETE a closed incident, bypassing the immutability business rule.

⬆️ Vertical Escalation — Exercise 1.2 (Urgency Close): The onUpdate handler at lines 24–27 fetches only status_code and rejects already-closed incidents. It does not check urgency_code === 'H' before permitting a support user to set status_code = 'C' on a High-urgency incident — an admin-only operation.

Evidence

  • srv/services.cds:8–10 — @requires: 'support' with no @restrict where clause; confirmed via grep returning zero results for @restrict
  • srv/services.js:6 — this.before("UPDATE", "Incidents", ...) — only UPDATE registered, no DELETE handler present
  • srv/services.js:24–27 — onUpdate queries only status_code; no urgency_code fetch or req.user.is('admin') check

Attack Precondition

Horizontal: any support role holder — no additional steps required. Vertical (DELETE closed): support user + UUID of a closed incident via standard OData DELETE. Vertical (urgency close): support user sends UPDATE with status_code = 'C' on a High-urgency incident.

Recommendation

  1. Add @restrict: [{ grant: 'READ', to: 'support' }, { grant: ['UPDATE', 'DELETE'], to: 'support', where: 'assignedTo = $user or assignedTo is null' }] to Incidents in srv/services.cds
  2. Extend handler registration to cover DELETE: this.before(["UPDATE", "DELETE"], "Incidents", ...)
  3. In the handler, also query urgency_code and add: if incoming status_code === 'C' and current urgency_code === 'H', verify req.user.is('admin') — reject with 403 if not

Plaintext Credit Card Numbers in Seed Data and Schema Critical
A04:2025 Cryptographic Failures Impact: Significant Ease: Easy Data Layer / Database Schema

Description

db/data/sap.capire.incidents-Customers.csv commits three real-format 16-digit PANs to source control in plaintext. The schema defines creditCardNo: String(16) with no encryption annotation and no @PersonalData.IsPotentiallySensitive label — so CAP's automatic audit-log and data-privacy manager integration is not activated. In production, the HANA database stores these values unencrypted. Database backups and the SQL injection in Finding #1 provide direct exfiltration paths.

Evidence

  • db/data/sap.capire.incidents-Customers.csv:2–4 — PANs 4111111111111111, 5500000000000004, 3400000000000094 in plaintext source-controlled CSV
  • db/schema.cds:31 — creditCardNo: String(16) with no encryption annotation
  • grep for @PersonalData across all .cds and .js files returns zero results

Attack Precondition

Read access to the git repository (for seed data). In production: read access to HANA database or its backups. Via Finding #1: any admin-role user can exfiltrate all customer records including PANs via SQL injection.

Recommendation

  1. Remove real card numbers from seed data — replace with synthetic test values (e.g., 4111111111111111 → 0000000000000000)
  2. Annotate creditCardNo with @PersonalData.IsPotentiallySensitive in db/schema.cds
  3. Add @cap-js/audit-logging and bind to SAP Audit Log Service to activate automatic field-access audit trails
  4. Implement field-level encryption or masking via SAP BTP data-privacy capabilities
  5. Restrict creditCardNo projection to roles that genuinely require it

No Security Headers Middleware High
A02:2025 Security Misconfiguration Impact: Moderate Ease: Easy Express Application Server

Description

The application uses Express via @sap/cds but no security header middleware is configured. helmet is not listed as a dependency and is not imported or registered anywhere. No Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, or Strict-Transport-Security headers are set. All HTTP responses are served without protective browser-security headers, leaving users vulnerable to clickjacking, MIME-sniffing, and protocol downgrade attacks.

Evidence

  • srv/services.js — no helmet import or app.use(helmet()) registration
  • package.json — helmet absent from both dependencies and devDependencies
  • grep for helmet, Content-Security-Policy, X-Frame-Options across srv/ returns zero matches

Attack Precondition

Any user accessing the application in a browser. Clickjacking requires only an attacker-controlled page that embeds the application in an iframe. No authentication required.

Recommendation

  1. Add helmet to production dependencies: npm install helmet
  2. Register it in the CAP bootstrap: cds.on('bootstrap', app => app.use(require('helmet')()))
  3. Configure a Content Security Policy appropriate to the SAP UI5 frontend (allow ui5.sap.com, SAP CDN origins)
  4. Enable HSTS with includeSubDomains for production BTP deployments

No Audit or Structured Security Event Logging High
A09:2025 Security Logging & Alerting Failures Impact: Moderate Ease: Easy Application Logging

Description

The application has no structured security event logging. All logging uses console.log and console.error — not tamper-evident, not persistent, and not routed to a SIEM. srv/services.js:41 logs the full raw SQL query string including user-supplied input to stdout, potentially leaking injected payloads into log aggregators. No @PersonalData annotations exist, so CAP's automatic audit-log integration is not enabled. No @cap-js/audit-logging or SAP Audit Log Service binding is present in mta.yaml. 403 rejections, auth failures, and sensitive data access leave no persistent audit trail.

Evidence

  • srv/services.js:38,41,44,47,54,57,63,66,69 — all logging via console.log/console.error
  • srv/services.js:41 — console.log('❌ Vulnerable query constructed:', vulnerableQuery) — logs raw SQL including user input
  • mta.yaml — no @cap-js/audit-logging module or SAP Audit Log Service resource binding
  • grep for @PersonalData across all .cds and .js files returns zero results

Attack Precondition

No precondition — the absence of logging means all attacks and anomalies go undetected regardless of sophistication or scale.

Recommendation

  1. Add @cap-js/audit-logging to dependencies and bind to SAP Audit Log Service in mta.yaml
  2. Annotate PII/sensitive fields with @PersonalData.IsPotentiallySensitive in db/schema.cds
  3. Replace console.* with structured CDS logging: const LOG = cds.log('security')
  4. Log all 403/401 events with user identity, endpoint, and timestamp
  5. Never log raw SQL query strings containing user-supplied input

Mocked Authentication with Hardcoded Credentials in Source Control Medium
A07:2025 Authentication Failures Impact: Significant Ease: Complex Authentication / package.json

Description

package.json lines 31–50 define a [development] CDS profile with auth.kind: "mocked" containing hardcoded users: incident.support@tester.sap.com with password: "initial" and the admin role, and alice / bob with the support role — all committed to version control. If the application is accidentally started in development mode in a network-accessible environment, these credentials bypass XSUAA entirely and grant full admin access without any token validation.

Evidence

  • package.json:31–50 — auth.kind: "mocked" with hardcoded users, passwords, and role assignments committed to source control
  • package.json:36 — "password": "initial" for the admin-role user

Attack Precondition

Application started with NODE_ENV=development or CDS_ENV=development in a network-accessible environment, or repository read access to harvest credentials for other attack vectors.

Recommendation

  1. Move all development auth configuration to .cdsrc-private.json or .env — both excluded from source control via .gitignore
  2. Never commit passwords to package.json
  3. Enforce production XSUAA auth mode in CI/CD by validating CDS_ENV=production before any deployment step

Committed Pre-Built Binary Artifact (.mtar) Medium
A03:2025 Software Supply Chain Failures Impact: Moderate Ease: Complex Supply Chain / Build Artifacts

Description

mta_archives/incident-management_1.0.0.mtar is a pre-built Multi-Target Application archive committed to the repository. Binary artifacts cannot be audited from source — their contents may differ from the current codebase, include outdated or vulnerable dependency versions, or have been tampered with after build. Additional zip build artifacts are also committed under gen/app/, app/incidents/dist/, and resources/.

Evidence

  • mta_archives/incident-management_1.0.0.mtar — binary .mtar committed to repository root
  • gen/app/incidents.zip, app/incidents/dist/incidents.zip, resources/incidents.zip — committed build output artifacts

Attack Precondition

The .mtar is deployed to SAP BTP instead of a freshly built artifact, or an attacker with repository write access substitutes a malicious archive that is then deployed without source-build validation.

Recommendation

  1. Add mta_archives/ to .gitignore and remove the committed binary from version control
  2. Build the .mtar in the CI/CD pipeline using mbt build
  3. Add a checksum verification step to the deployment pipeline
  4. Consider signing build artifacts and verifying signatures at deploy time

No SCA Scanning and Floating Dependency Version Ranges Medium
A03:2025 Software Supply Chain Failures Impact: Moderate Ease: Advanced Supply Chain / package.json

Description

No Software Composition Analysis tool is configured in the repository (no .snyk, dependabot.yml, or renovate.json). All four production dependencies use caret (^) version ranges, permitting automatic resolution of minor and patch versions that may introduce vulnerabilities without detection. No SBOM is generated. The mta.yaml build commands run only npm ci and npx cds build — no SCA step is present.

Evidence

  • package.json:9–12 — "@sap/cds": "^10", "express": "^4", "@cap-js/hana": "^3", "@sap/xssec": "^4" — all caret ranges
  • No .snyk, dependabot.yml, or renovate.json found in the repository
  • mta.yaml:13–14 — build commands: npm ci and npx cds build --production only, no SCA step

Attack Precondition

A dependency (direct or transitive) is updated to a version containing a vulnerability or malicious code. Without SCA, this goes undetected until active exploitation occurs.

Recommendation

  1. Configure Snyk or GitHub Dependabot for automated vulnerability scanning on every PR
  2. Add an SCA step (e.g., npx snyk test) to mta.yaml build commands before the build step
  3. Generate an SBOM with npm sbom on each release
  4. Consider pinning critical production dependencies to exact versions
