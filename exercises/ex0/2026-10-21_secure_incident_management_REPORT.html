SQL Injection in AdminService.fetchCustomer Critical
A05 Injection Impact: Severe Ease: Easy AdminService (srv/services.js)

Description

AdminService.fetchCustomer builds raw SQL queries via template literal string interpolation of the user-supplied customerID parameter and passes the result directly to cds.run(). Both concat and tagged execution methods are vulnerable. The tagged method superficially mimics a tagged template literal but invokes sql() as a plain function with a pre-interpolated string — no sanitization occurs. An attacker with admin credentials can inject SQL predicates (e.g., ' OR '1'='1) to exfiltrate all customer records including credit card numbers.

Evidence

  • srv/services.js:40 — template literal SELECT * FROM ... WHERE ID = '${customerID}' passed to cds.run()
  • srv/services.js:43 — const results = await cds.run(vulnerableQuery);
  • srv/services.js:62 — same pattern via fake tagged-template: sql(...) called with pre-interpolated string
  • srv/services.js:55–61 — sql() function receives a plain string (not TemplateStringsArray); no sanitization occurs

Attack Precondition

Authenticated admin user. Admin credentials are available in the mocked auth configuration (package.json:35–38). OData GET to /odata/v4/admin/fetchCustomer(customerID='...',method='concat').

Recommendation

  1. Replace both methods with parameterized CAP CQL: SELECT.from(Customers).where({ID: customerID}) or the tagged template form SELECT.from(Customers).where`ID = ${customerID}`.
  2. Remove the fetchCustomer raw SQL function entirely if a filtered OData query on Customers achieves the same purpose.
  3. If a custom function is required, use db.run(SELECT.from('sap.capire.incidents.Customers').where({ID: customerID})) — never build raw SQL strings from user input.

Missing Row-Level Access Control on Incidents — Horizontal & Vertical Escalation Critical
A01 Broken Access Control A06 Insecure Design Impact: Significant Ease: Easy ProcessorService

Description

🔁 Horizontal Escalation (Ex 1.1): ProcessorService.Incidents uses @requires: 'support' only — no @restrict where clause is present. @requires is authentication (verifies the role exists), not authorization (does not restrict rows). Any support user can READ, UPDATE all incidents regardless of ownership. grep -n "@restrict" srv/services.cds returns no results — Exclusion 5 precondition not met.

⬆️ Vertical Escalation (Ex 1.2): The handler registers this.before("UPDATE", "Incidents") only — no DELETE handler. Support users can DELETE any incident including closed incidents and those assigned to other users with no guard. The closed-incident status check fires only on UPDATE.

Evidence

  • srv/services.cds:8 — @requires: 'support' with no @restrict where clause
  • srv/services.cds:10 — entity Incidents as projection on my.Incidents; — no row-level filter
  • srv/services.js:6 — this.before("UPDATE", "Incidents", ...) — DELETE not included
  • srv/services.js:24–28 — closed-incident guard exists for UPDATE only; no equivalent DELETE handler

Attack Precondition

Authenticated support user. For horizontal escalation: OData READ/PATCH to /odata/v4/processor/Incidents with no filter returns all incidents. For vertical escalation: OData DELETE to /odata/v4/processor/Incidents(ID) for any incident — including closed ones or those owned by others.

Recommendation

  1. Replace @requires: 'support' on Incidents with a full @restrict annotation including a where: 'assignedTo is null or assignedTo = $user' clause for UPDATE and DELETE operations.
  2. Register a combined UPDATE+DELETE handler: this.before(['UPDATE', 'DELETE'], 'Incidents', (req) => this.onModify(req)).
  3. In onModify, check both ownership and closed-status for DELETE as well as UPDATE.
  4. Add the admin full-access grant: { grant: '*', to: 'admin' }.

Hardcoded Mocked Credentials with Admin Role in package.json Critical
A07 Authentication Failures Impact: Severe Ease: Advanced Authentication (package.json)

Description

package.json commits a [development] CAP auth configuration with kind: "mocked" defining user incident.support@tester.sap.com with password: "initial" and roles: ["admin"]. CAP mocked authentication activates whenever no XSUAA service binding is present. Any deployment without a valid XSUAA binding — including staging environments, CI runners, or misconfigured BTP spaces — accepts these known credentials and grants full admin access including access to AdminService and the SQL injection vector (Finding #1).

Evidence

  • package.json:33 — "kind": "mocked"
  • package.json:35–38 — "password": "initial", "roles": ["admin"]
  • package.json:55–57 — "auth": "xsuaa" for production; no startup assertion that the binding is present

Attack Precondition

Deployment environment missing XSUAA service binding. Repository read access to discover the credentials (incident.support@tester.sap.com / initial). Mocked auth is the default CAP fallback when no XSUAA binding is detected.

Recommendation

  1. Move mocked user configuration to .cdsrc-private.json or a .env file and add both to .gitignore.
  2. Enforce startup failure if VCAP_SERVICES does not contain a valid XSUAA binding in production/staging profiles.
  3. Change the password from the well-known default "initial" to a randomly generated value.
  4. Do not assign the admin role to the mocked development user; use a minimal-privilege role for testing.

Plaintext Credit Card Numbers in Seed Data Critical
A04 Cryptographic Failures Impact: Significant Ease: Easy Data Layer (db/schema.cds, db/data/)

Description

db/data/sap.capire.incidents-Customers.csv contains real-format 16-digit PANs in plaintext (Visa test PAN 4111111111111111, Mastercard test PAN 5500000000000004). The creditCardNo field in db/schema.cds:31 has no @PersonalData.IsPotentiallySensitive annotation and no encryption-at-rest directive. Support users have read-only access to Customers via ProcessorService.Customers. Plaintext PAN storage violates PCI-DSS requirements.

Evidence

  • db/data/sap.capire.incidents-Customers.csv:2–4 — plaintext PANs 4111111111111111, 5500000000000004
  • db/schema.cds:31 — creditCardNo : String(16) — no @PersonalData annotation
  • srv/services.cds:13–14 — Customers exposed to support role (read-only)

Attack Precondition

Repository read access (seed CSV data) OR authenticated support/admin role reading Customers entity via OData. No additional privileges required beyond repository clone or valid login.

Recommendation

  1. Annotate creditCardNo with @PersonalData.IsPotentiallySensitive to enable CAP audit logging for reads/writes.
  2. Replace real-format PANs in seed data with clearly fictional values (e.g., 0000000000000000).
  3. Add a masked projection in ProcessorService.Customers that excludes creditCardNo entirely.
  4. In production, store only the last 4 digits or a tokenized reference; do not persist the full PAN.

No Software Composition Analysis (SCA) Tool Configured Medium
A03 Software Supply Chain Failures Impact: Moderate Ease: Advanced Package Management (package.json)

Description

No SCA tool configuration exists. There is no .snyk file, no dependabot.yml, no renovate.json, and no FOSSA or Mend configuration. All production dependencies use floating ^ semver ranges ("@sap/cds": "^10", "express": "^4", etc.). A CVE in a direct or transitive dependency would not be automatically detected or flagged before deployment.

Evidence

  • package.json:9–12 — all production dependencies use ^ ranges
  • Directory .github/ — does not exist; no Dependabot configuration
  • File .snyk — does not exist
  • File renovate.json — does not exist

Attack Precondition

Vulnerable transitive dependency introduced via supply chain compromise or unpatched CVE. No automated CI gate to block deployment of vulnerable builds.

Recommendation

  1. Add .github/dependabot.yml to enable weekly npm dependency security alerts.
  2. Add OWASP Dependency-Check or Snyk to the CI/CD pipeline to audit on every build.
  3. Consider pinning critical production dependencies to exact versions for reproducibility.
  4. Add npm audit as a pre-build step in mta.yaml's before-all commands.

External SAPUI5 CDN Script Loaded Without Subresource Integrity Medium
A08 Software or Data Integrity Failures Impact: Significant Ease: Complex Frontend (app/incidents/webapp/index.html)

Description

app/incidents/webapp/index.html loads sap-ui-core.js from the external CDN sapui5.hana.ondemand.com without an integrity attribute (Subresource Integrity — SRI). A CDN compromise or MITM could deliver a tampered script that executes arbitrary JavaScript in every user's session. The version is pinned to 1.138.0, which limits CDN-side auto-update risk but does not protect against active CDN compromise.

Evidence

  • app/incidents/webapp/index.html:13–24 — <script src="https://sapui5.hana.ondemand.com/1.138.0/resources/sap-ui-core.js"> — no integrity= or crossorigin= attributes

Attack Precondition

CDN compromise or network-level MITM for sapui5.hana.ondemand.com. Version is pinned so automatic CDN-side substitution does not apply; active exploitation required.

Recommendation

  1. Generate the SHA-384 hash of sap-ui-core.js@1.138.0 and add integrity="sha384-<hash>" crossorigin="anonymous" to the <script> tag.
  2. SAP publishes SRI hashes for UI5 CDN resources; use the official hash for the pinned version.
  3. Alternatively, bundle the UI5 resources locally as part of the npm run build step to eliminate the CDN dependency in production.

No Security Audit Logging for Access Control Events Medium
A09 Security Logging and Alerting Failures Impact: Minor Ease: Easy Service Layer (srv/services.js, mta.yaml)

Description

The application uses only unstructured console.log and console.error throughout srv/services.js. There is no cds.log structured logger, no SAP Audit Log Service binding in mta.yaml, no @cap-js/audit-logging dependency, and no @PersonalData annotations on creditCardNo. 403 rejections are not logged to any tamper-evident store. Without security event logging, privilege escalation attempts, injection attacks, and unauthorized access are invisible to incident responders.

Evidence

  • srv/services.js:38–69 — console.log/console.error throughout; no cds.log() usage
  • mta.yaml — no application-logs or audit-log service resource defined
  • db/schema.cds:31 — creditCardNo has no @PersonalData.IsPotentiallySensitive annotation

Attack Precondition

Any attacker performing unauthorized access attempts. The absence of detection means forensic reconstruction of an incident is impossible after the fact.

Recommendation

  1. Replace all console.log/console.error with const LOG = cds.log('incidents') and use structured context fields (user, operation, resource ID, outcome).
  2. Add @cap-js/audit-logging as a dependency and wire it in package.json cds.requires.
  3. Add an application-logs or audit-log service binding resource to mta.yaml.
  4. Annotate creditCardNo with @PersonalData.IsPotentiallySensitive to enable automatic CAP field-access audit logs.
  5. Log 403 rejections in onUpdate (and the future onModify) with user ID and incident ID.

Pre-built Binary MTA Archive Committed to Repository Low
A03 Software Supply Chain Failures Impact: Minor Ease: Complex Build/Deploy (mta_archives/)

Description

mta_archives/incident-management_1.0.0.mtar is a pre-built MTA archive committed to the repository. Binary artifacts cannot be audited from source and may contain dependency versions that differ from those currently in package-lock.json. Committing build artifacts bypasses CI/CD integrity controls and may embed outdated or vulnerable dependencies frozen at build time.

Evidence

  • mta_archives/incident-management_1.0.0.mtar — binary archive committed to repository
  • mta.yaml:12–13 — correct CI build process defined (npm ci + npx cds build --production) but pre-built artifact could be deployed directly

Attack Precondition

Developer or CI deploys the committed .mtar directly rather than rebuilding from source. The artifact's dependency tree may differ from the current lockfile.

Recommendation

  1. Add mta_archives/ to .gitignore immediately.
  2. Build the .mtar artifact in the CI/CD pipeline using mbt build and publish it as a pipeline artifact.
  3. Never commit pre-built archives to source control; use a binary repository (Nexus, Artifactory, SAP BTP Piper) for release artifacts.
